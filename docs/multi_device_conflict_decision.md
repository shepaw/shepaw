# 多端消息同步：冲突到底存不存在

状态：**R1 已实施**（2026-10-15 裁定：① 已读=主机权威 ② 不做标未读入口 ③ 删除上行暂缓）
已定：① 不需要版本向量 / CRDT，理由见 §三；② 冲突面比原审查报告的判断窄得多——真正需要定口径的只有两类本地可写状态，见 §二；③ 已读走 §6.1 的 B1
范围：App `lib/peer/services/peer_agent_client_service.dart`、`lib/peer/pouch_turn_relay.dart`、`lib/services/database/channel_dao.dart`；主机 `shepaw-cli/crates/she/src/chat.rs`、`crates/api/src/agent.rs`
相关：`docs/roadmap_host_authority.md`（总纲，冲突时以它为准）、`docs/session_history_authority_decision.md`

## 一、问题

多端消息同步审查里，我把「完全没有冲突解决」列为 P1 缺陷：两端并发改同一会话必丢一端。写这份文档前逐条核查了写入路径，**结论要修正**——大部分实体根本不存在两端并发写，剩下的也不是经典的「值冲突」，而是「本地状态能不能上行」。

另：审查里发现的同步可靠性问题（丢帧不可检测、事件日志裁剪后 `reset` 无人处理、`ChatLog::append` 无锁、群事件序号与落盘顺序错位、水位记在本机时钟）**已经修完并分轮提交**，不在本文档范围内。本文档只谈「谁说了算」。

## 二、核查：每条写入路径的权威在哪

| 实体 | 谁写 | 权威 | 两端会并发写吗 |
| --- | --- | --- | --- |
| 消息正文（agent 输出） | 主机（引擎回合） | 主机 | 否，主机单写 |
| 消息正文（用户发送） | 客户端本地乐观插入 + 主机落库 | 主机 | **不会冲突**，见关键事实 1 |
| 群注册表 | 主机（`crates/groups`） | 主机 | 否，`gate` 串行 |
| 会话元数据（标题等） | 主机 | 主机 | 否 |
| 已读状态 | 客户端上行 + 主机水位 | 未定 | **是**，见 §4.1 |
| 消息存在性（删除） | 客户端本地 | 无 | **是**，见 §4.2 |

**关键事实 1：用户消息不会产生两条，也不会互相覆盖。** 客户端发送前预生成 `userMessageId`（`agent_messaging_service.dart:517`），主机落库时沿用这个 id（`crates/she/src/turn.rs:1512-1515`）。所以两台设备各发一条是两条不同 id，而同一条消息在任何一端落库都用同一个 id，`ConflictAlgorithm.ignore` 天然幂等。

**关键事实 2：App 没有用户主动删除/编辑消息的入口。** 全仓唯一的删除调用在重答流程里，删的是刚收到的 agent 响应（`chat_controller_messaging.dart:1091`）。

**关键事实 3：群与会话元数据一律主机写。** `gate` Mutex 串行，且事件序号已在锁内分配（本次修复），不存在写入与广播错位。

⇒ 于是「冲突」只剩两类：**已读状态**和**消息存在性**。而且它们都不是「两端同时改同一字段、需要裁决谁赢」，而是「本地改了，主机不知道」。

## 三、为什么不做版本向量 / CRDT

1. **和总纲冲突。** 总纲一句话定了架构：「主机持有会话与消息，App 只负责连上去拉数据渲染」。版本向量意味着客户端获得裁决权。
2. **收益只覆盖两个字段。** 消息正文、群、会话元数据都不需要它（§二）。为已读和删除引入全局版本机制，投入产出不成立。
3. **已读本质不是值冲突。** 主机记的是 `read_at` 水位（`crates/api/src/agent.rs` 的已读水位），两端都标已读时取较新的即可——没有需要裁决的分歧，需要的是「水位往哪边对齐」这个口径。

## 四、三处真正的不一致

### 4.1 已读：现在是「本地优先」，和主机权威相反

重同步时判断一条消息要不要回写（`peerHistoryRowNeedsWrite`，`peer_agent_client_service.dart:506-531`）：

- 远端 `is_read = true` 且本地未读 → 写（`:521-523`）
- **本地已读、远端未读 → 不回写**（规则里没有这条分支）

也就是本地已读状态永远不会被远端覆盖。后果：一端把会话标成已读后，即便主机侧水位回退（或别的端标了未读），这台的角标也永远是干净的。

上行方向是通的：`mark_read` 有 pending_ops Outbox 离线补发（`pouch_turn_relay.dart:278-415`）。问题只在下行覆盖口径。

### 4.2 删除只删本地，主机还留着

重答流程 `deleteMessage`（`chat_controller_messaging.dart:1091`）只删本地行，主机 transcript 里那条还在。下次按 id 对齐的 transcript 同步会把它**拉回来**——用户看到删掉的回复又出现了。

### 4.3 Outbox 是通用的，但只有 mark_read 在用

`pending_ops` 表支持任意 `kind`（`channel_dao.dart:1042-1092`），目前唯一生产者是 `mark_read`（`pouch_turn_relay.dart:441`）。将来「删除上行」要复用这张表，不用另建一套。

## 五、三个方案

| | A 版本向量 | B **收敛本地可写状态**（推荐） | C 不动 |
| --- | --- | --- | --- |
| 做法 | 每条消息带版本号，同步时三方合并，UI 处理冲突态 | 明确「客户端只有两种本地可写状态」，两者都上行；其余一律主机权威 | 维持现状 |
| 与总纲 | 冲突 | 一致 | 一致 |
| 改动量 | 大（schema + 协议 + UI 冲突态） | 中（一条删除帧 + 墓碑 + Outbox 接删除） | 0 |
| 能解决 | 4.1 / 4.2 / 4.3 | 4.1 / 4.2 / 4.3 | 都不能 |

**推荐 B。** 它不引入新机制，只是把已经存在的事实（客户端几乎不持有可写状态）写进代码和文档，再把两个漏网的补齐。

## 六、方案 B 的关键设计

### 6.1 已读：已定 B1 主机权威

**裁定：B1。** 本地已读也以主机为准，远端说没读就跟过去。这和总纲一致，而且「手机上看了、电脑上还是未读」本身就是用户会抱怨的。

实现时加了一道保护（`peerHistoryRowNeedsWrite` 的 `keepLocalRead`）：**本地还有 mark_read 没补发出去时不撤销本地已读**。那时远端未读只是上行迟到，不是主机否定了已读——跟过去会让红点莫名复活，等补发成功再标回去。判据是 `pending_ops` 里这个会话有没有待补发的 mark_read（`_hasPendingReadFor`）。

注意 B1 只影响「content 没变、纯粹是已读状态不同」这种情况；content 变了本来就会整行重写，is_read 一直跟随远端。

### 6.2 删除：墓碑 + 上行 + 广播

本地不真删，改成插墓碑（消息仍在，标记 `deleted_at`）→ 上行一条删除帧 → 主机删 + 广播 → 各端按 id 删。离线时进 `pending_ops`，和 mark_read 共用补发通道。

好处是幂等：重复删同一 id 没有副作用，所以补发不需要去重键。

### 6.3 把「本地可写状态」写成清单

在文档和代码注释里固定下来：客户端对消息**只有**已读、删除两种可写状态，都必须上行；新增任何本地写都要先回答「主机怎么知道」。

## 七、分轮落地（建议）

| 轮 | 内容 | 风险 |
| --- | --- | --- |
| R1 | §6.1 口径定下来后统一已读的覆盖规则（改 `peerHistoryRowNeedsWrite`） | 低，纯规则 |
| R2 | 删除上行：主机加删除帧 + 本地墓碑 + `pending_ops` 接删除 | 中，涉及 schema 加列 |
| R3 | 补测试：两端并发标已读/删除后的收敛 | 低 |

R1 是 R2 的前置（先定方向，再动删除）。

## 八、裁定结果（2026-10-15）

1. **已读谁说了算** → **B1 主机权威**，配 §6.1 的 pending 保护。R1 已实施。
2. **标未读入口** → **不做**。那么 §4.1 里「一端标未读另一端不知道」这条不成立，已读的唯一流向就是单调上行，B1 的负面面进一步收窄。
3. **删除上行** → **暂缓**（R2）。目前只有「历史补充重答」会触发本地删除（`chat_controller_messaging.dart:1091`），很边缘，且没有用户主动删除入口。真要处理时更省事的选项是本地别真删——旧回答与新回答并排显示，像别的客户端的「重新生成」那样，但那是 UI 取舍，另议。

R3 随 R1 做了纯函数层的两条用例；端到端并发测试留到做 R2 时一起。
